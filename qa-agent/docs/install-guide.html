Installation Guide

Install the QA
AZM Digital Agent

From git clone to a finished project setup — eight steps, roughly fifteen minutes, once per machine. After this, /qa-run works in every project you open.

8 agents 2 commands 8 helper tools Windows · PowerShell 5.1 ~15 min
Step 0

Before you start

Tick these off first. Every one of them is a real dependency — skipping one produces an error later that looks like something else.

  • ✓Windows + VS Code + the Claude Code extensionThe agent is a Claude Code framework. It runs inside VS Code, not as a standalone CLI.
  • ✓PowerShell 5.1 (built into Windows)Invoke it as powershell, never pwsh — many Windows machines ship only 5.1 and pwsh is not on PATH.
  • ✓Node.jsThe helper tools (aio-sync.js, embed-screenshots.js, the report generators) are Node scripts the agents shell out to.
  • ✓Git — optionalOnly if you clone. The ZIP download path needs no Git at all.
  • ✓A Jira story to test, and access to its projectThe pipeline starts from a story key such as PROJ-123.
⚠ The one mistake everybody makes exactly once

There are two different places you type things. Mixing them up gives a “term is not recognized” error that sends people hunting for a broken install that isn't broken.

What you typeWhere it goes
git clone, install.ps1, Get-ChildItemVS Code terminal / PowerShell — real shell commands
/qa-setup, /qa-run PROJ-123The Claude Code chat box (Ctrl+Esc) — these are Claude Code commands, not shell commands

/qa-run will never work in PowerShell. Type / in the Claude Code chat to see the commands listed.

1
≈ 2 minutes

Get the agent code

Both routes give you the same qa-agent/ folder holding all 8 agents, both commands and the installer. There is nothing to build or compile — the agents are markdown files.

PowerShell
PS> git clone https://github.com/UsamaArshadJadoon/ManualTestingAgent.git
PS> cd ManualTestingAgent

Clone anywhere you like — C:\ManualTestingAgent is a good neutral home. The folder is only the source; the next step copies what matters into your user profile.

On the repo page press the green Code button → Download ZIP, then right-click the file → Extract All.

Paste this whole block into PowerShell. It downloads main, extracts it, and installs everything in one go — steps 1 and 3 together.

PowerShell — download & install
# QA AZM Digital Agent — one-shot download & install
$zip  = "$HOME\Downloads\qa-azm-agent.zip"
$dest = "$HOME\Downloads\qa-azm-agent"
Invoke-WebRequest "https://github.com/UsamaArshadJadoon/ManualTestingAgent/archive/refs/heads/main.zip" -OutFile $zip
Expand-Archive $zip $dest -Force
$root = (Get-ChildItem $dest -Directory)[0].FullName
powershell -ExecutionPolicy Bypass -File "$root\qa-agent\install.ps1"
Install from main, not from a release tag

Tags go stale fast, and a stale install here is not cosmetic. Earlier versions shipped bugs that blocked every test case on password-less logins and wrote permanently wrong data into AIO Tests — which has no delete endpoint, so those mistakes cannot be undone. If change control forces you to pin a version, re-check it against main before rolling it out.

2
≈ 3 minutes

Authorize the connectors

Two connectors carry the whole pipeline. Without them the run stops at its first Jira contact or its first browser action — so do this before the first run, not during it.

Atlassian (Jira)

Used by qa-story to read the story, qa-bug-logger to file bugs, qa-validator to re-check against the source, and qa-test-sync to link AIO cases back to the story.

Playwright

Used by qa-test-executor to drive a real browser through the mcp__playwright__* tools and capture full-page HD evidence.

How you'll know it worked

If Atlassian isn't authorized, /qa-run stops on its first Jira contact and tells you to authorize it — it doesn't fail silently or guess. Re-run after connecting.

≈ 1 minute

Install the agents

Open PowerShell inside the folder that contains qa-agent\ and run the installer. This is the step that makes the agents global.

PowerShell — run from the repo root
PS> powershell -File qa-agent\install.ps1

Blocked by execution policy? Use the bypass form — it applies to this one invocation only and changes nothing machine-wide:

PowerShell — if the policy blocks scripts
PS> powershell -ExecutionPolicy Bypass -File qa-agent\install.ps1

What it actually does

It is a plain copy — no build, no package manager, no network call:

From the repoTo your profileWhat it is
qa-agent\agents\*.md~\.claude\agents\The 8 subagents
qa-agent\commands\*.md~\.claude\commands\/qa-run and /qa-setup
qa-agent\tools\*~\.claude\qa-agent\tools\Node/PS helpers the agents shell out to

Tools land under ~\.claude\qa-agent\ rather than beside the agents deliberately: a globally-installed agent must find aio-sync.js from any project, not only from a checkout of this repo.

If it warns about orphans, read it

The installer also checks for qa-*.md files in ~\.claude\agents that this framework no longer ships. Those are leftovers from an older version — and they stay dispatchable, so a stale orchestrator can be invoked by mistake and quietly contradict the current pipeline. The script prints a ready-made Remove-Item line for each; it never deletes from your home directory on its own.

Updating later

Pull or re-download, then run the same command again. It overwrites the deployed copies with the current ones — there is no uninstall step and no version state to reconcile.

5
≈ 3 minutes

Set up your project

The machine-wide install is done. Everything from here is per project. Open the project you want to test and run /qa-setup in the Claude Code chat — not the terminal.

What it writes

.qa-config.json

Jira project + site, app URL, login shape, safety switches. Env-var names only — never values.

.qa-secrets

Git-ignored KEY=VALUE store, scaffolded empty. You fill it in privately.

.gitignore

Hardened so secrets, config, browser snapshots and run outputs can never be committed.

It never asks for a password. The interview collects only the name of the environment variable that will hold each credential. A real secret should never pass through a chat transcript.

.qa-config.json — the shape it produces
{
  "jira": { "projectKey": "PROJ", "defaultBugType": "Bug",
             "siteUrl": "https://your-site.atlassian.net", "cloudId": "…" },
  "app": {
    "baseUrl": "https://uat.example.com",
    "login": {
      "required": true,
      "loginUrl": "https://uat.example.com/login",
      "usernameEnv": "QA_USER_ID",
      "passwordEnv": null,          // passwordless: no password exists
      "passwordless": true,
      "notes": "Which field takes the identifier, what submit is called…",
      "sessionReuse": true
    }
  },
  "safety": { "allowProduction": false, "destructiveActions": "confirm", … },
  "outputDir": "qa-runs"
}
Passwordless logins are first-class — say so explicitly

Plenty of UAT environments authenticate on an identifier alone: a identifier, national ID or employee number, with the password step bypassed. Set passwordEnv: null and passwordless: true, and name usernameEnv for what it really holds. Do not invent a placeholder password name — that makes the executor hunt for a credential nothing will ever set, and it will block your cases over it.

6
≈ 1 minute

Provide the credentials

Two options, and the executor checks them in this order: OS environment variable first, then .qa-secrets. Use whichever suits you — they are interchangeable.

Convenient for repeated runs and never committed. Fill in the values after the =:

.qa-secrets — passwordless example
# QA Orchestrator credential store — .env-style KEY=VALUE
# Git-ignored. MUST NEVER be committed.
QA_USER_ID=<your identifier — never commit this>
# Only needed when aio.enabled is true
AIO_TOKEN=

Keys must match the *Env names in .qa-config.json exactly. For a password-based login the pair is QA_USER / QA_PASS by default.

Nothing on disk — the values live only in that shell session:

PowerShell
# passwordless — identifier only
PS> $env:QA_USER_ID = "your-user-id"

# or a classic username + password login
PS> $env:QA_USER = "your-username"
PS> $env:QA_PASS = "your-password"
How the credential is handled

Read once by qa-test-executor at login time through a narrowly-scoped capability, held in memory for the login step only, and masked out of every report, bug and screenshot. It is never written to results.json, the run folder, or any artifact. The browser-snapshot scratch directory is deleted after each run.

7
optional · ≈ 3 minutes

AIO Tests sync

Skip this entirely if you don't use AIO Tests. When enabled, qa-test-sync mirrors the approved cases into the story's AIO folder and links each one back to the Jira story.

.qa-config.json — the aio block
"aio": {
  "enabled": true,
  "baseUrl": "https://tcms.aiojiraapps.com/aio-tcms/api/v1",
  "tokenEnv": "AIO_TOKEN",
  "projectKey": "PROJ",
  "scriptTypeId": null,     // leave null — see the warning below
  "linkToStory": true
}
⚠ Leave scriptTypeId as null

The id of the “Classic” script type is per-project configuration, not a constant — the number that means Classic in one project can mean a different test type in another. Pin the wrong one and every case fails with Invalid or missing value for Test Script Type. Left null, the script discovers the real id from an existing case in the same project and refuses to guess when it can't.

This matters more than it sounds: AIO has no DELETE endpoint for test cases. A wrong POST creates a permanent case you cannot remove through the API.

Create the folder first — the API cannot

Before the run, create one folder in the AIO Cases module named with the story key. qa-test-sync finds it by name and fills it. If it's missing, the agent stops and tells you the exact name to create.

Finally, add the token to .qa-secrets under the name in tokenEnv:

.qa-secrets
AIO_TOKEN=<your AIO API token>

setup complete

Your first run

Setup is done. In the Claude Code chat — not PowerShell — point the orchestrator at a story key:

Claude Code chat  ·  Ctrl+Esc to focus
/qa-run PROJ-123

What happens next

Press play to watch the pipeline the single command drives:

qa-story→ qa-test-writer→ qa-gap-analyzer→ Gate 1 · you approve the plan→ qa-test-executor→ qa-bug-logger (draft)→ Gate 2 · you approve the bugs→ qa-bug-logger (file)→ qa-reviewer · GO / NO-GO

Three points where it stops for you

Nothing touches your app before Gate 1. Nothing reaches Jira before Gate 2. And if a stage still fails validation after two automatic retries, it stops and asks rather than pressing on.

Useful flags

--resume continues an interrupted run from the first missing stage. --rerun re-tests only what's unresolved — failed, flaky or blocked.

Where the results land

qa-runs/ — one timestamped folder per run
qa-runs/PROJ-123_20260727-143001/
  run-context.json      story.json         test-cases.json
  gap-report.json       results.json       screenshots/
  bugs-proposed.json    bugs-created.json  review.json
  validation/           aio-sync.json      # only when AIO is on
  report.md             report.html        bug-report.html

Every stage writes a file the next stage reads, so the run folder is the audit trail. report.html carries the verdict and the AC-to-test-to-result-to-bug traceability matrix; bug-report.html embeds every screenshot inline at full HD.

Troubleshooting

The failures people actually hit, and what each one really means.

qa-run is not recognized as the name of a cmdlet

You typed a Claude Code command into PowerShell. /qa-run and /qa-setup only exist in the Claude Code chat box — Ctrl+Esc to focus it. Only install.ps1 belongs in the terminal.

The / menu doesn't list qa-run or qa-setup

Reload the window: Ctrl+Shift+P → Developer: Reload Window. If they're still missing, the copy didn't land — re-run the verification in step 4 and check ~\.claude\commands actually holds the two .md files.

pwsh is not recognized

Use powershell, not pwsh. Many Windows installs ship only PowerShell 5.1, where pwsh isn't on PATH. Every command in this guide uses powershell for that reason.

Running scripts is disabled on this system

Execution policy. Use powershell -ExecutionPolicy Bypass -File qa-agent\install.ps1 — scoped to that single invocation, no machine-wide change.

The run stops saying Jira access was not granted

Either the Atlassian connector isn't authorized (step 2), or jira.siteUrl/cloudId is wrong. Every Atlassian call needs a cloudId; without a pinned site the agents have to guess a hostname, and a wrong guess surfaces as a confusing access-denied rather than a clear error.

Every test case comes back blocked on login

Classic passwordless misconfiguration. If the app takes an identifier only, passwordEnv must be null and passwordless must be true. A placeholder password name makes the executor wait on a credential that will never be set. Also confirm the key in .qa-secrets matches usernameEnv character for character.

Invalid or missing value for Test Script Type

A pinned aio.scriptTypeId that's wrong for this project. Set it back to null and let the script discover it. Do not start trying other numbers — every wrong POST that does succeed creates a permanent case AIO cannot delete via the API.

The run refuses to start against my URL

The production guard. safety.prodUrlPatterns matched your host (prod, www., app., live). If the target really is a test environment, adjust the patterns; if it really is production, you must set allowProduction: true deliberately.

Screenshots don't appear on the Jira bug

Known limitation, not a fault. The Atlassian connector cannot upload attachments, so filed bugs reference screenshots by run-folder path. Share the generated bug-report.html instead — it embeds every image inline at full HD — or attach the files to Jira by hand.
